# 9 規則の詳細

各規則について、目的、なぜ効くか、チェック観点、対象外の条件、別の表現で満たす条件、実装上の注意を示す。
チェック観点は、すべてを満たす必要はない。
規則の目的が達成されているかを判断するための問いであり、対象アプリに合わない観点は読み替えてよい。

「対象外」と「別の表現で満たす条件」は判定が異なる。

- **対象外**：その状態が起きない、または起きても利用者が困らない場合。判定は「適用しない」とし、理由を添える。
- **別の表現で満たす条件**：チェック観点どおりの表示はできないが、規則の目的を別の手段で達成できる場合。判定は「適用しない」にせず、その手段が実装されているかで「満たす」「満たさない」を決める。

## 01 待ち時間を見える化

**目的**：何を待っているか、どこまで進んだかが分かれば、利用者は待てる。分からなければ離脱する。

**なぜ効くか**：
利用者が待つのをやめるのは、待ち時間の長さそのものより「終わるかどうか分からない」不安が原因になることが多い。
画面全体を覆うスピナーは、何が起きているかも、あとどれくらいかも伝えない。
これから表示される内容の輪郭（スケルトン）と進捗（件数や割合）を見せれば、利用者は結果を予測でき、待つ判断ができる。

**チェック観点**：
- 待っている対象が分かるか（「一覧を読み込み中」「ファイルを送信中」など、何の処理かが画面から読み取れる）。
- 進捗が分かるか（件数、割合、残り時間のいずれか。分からない場合でも、段階が複数あるなら現在の段階）。
- これから表示される内容の輪郭が見えるか（テーブルなら列見出しと行のスケルトン、カードならカードの枠）。
- 待っている間に操作できる要素が明確か（ページャや絞り込みは待機中に使えるのか、無効化されているのか）。
- 処理を始めた操作の起点（ボタンやリンク）自体が処理中を示し、同じ操作を二度受け付けないようになっているか。
  押した直後に何も変わらないと、利用者は反応がないと思ってもう一度押す。
- 待ち時間が長引いたときの扱いがあるか（一定時間を超えたら、時間がかかっている旨とキャンセルや再読み込みの手段を出す）。

**対象外**：
- 待ち時間が体感できない長さ（目安として 1 秒未満）で、しかもほぼ常にそうである。
  この場合はスケルトンすら表示の点滅を生んで逆効果になる。
  一定時間（200 ミリ秒程度）経過してから表示する遅延を入れるのが妥当である。
  発生頻度が低くても、起きたときに長く待たせる処理（月次の集計、大きなファイルの送信など）は対象外にしない。

**別の表現で満たす条件**：
- 進捗を出す情報源がない（バックエンドが件数を返さず、追加するコストが見合わない）。
  処理名とスケルトンで「何を待っているか」は伝えられるので、それが実装されているかで判定する。
  進捗表示は追加開発の候補として分けて書く。

**実装上の注意**：
- スケルトンは実際の表示と同じレイアウトで作る。ずれると、表示の切り替わりで画面が跳ねる。
- 進捗の通知は `aria-busy` と `aria-live="polite"` の領域で支援技術に伝える。
- 段階的に読み込む場合、読み込み済みの部分は先に操作可能にできないかを検討する。
- 処理中のボタンは無効化するだけでなく、文言かアイコンで処理中だと示す。無効化だけでは、押せない理由が伝わらない。

## 02 空状態に次の行動を

**目的**：空白を行き止まりにせず、最初の操作へつなぐ。

**なぜ効くか**：
「データがありません」だけの画面は、利用者に「壊れているのか」「自分が何かを間違えたのか」「次に何をすればよいのか」を考えさせる。
空であることが正常で、次に取るべき操作が明示されていれば、利用者は立ち止まらずに進める。
初めて使う利用者が最初に見る画面が空状態であることも多く、ここでの案内が定着率に影響する。

**チェック観点**：
- 空であることが正常だと伝わるか（エラーと区別できる見た目と文言）。
- ここに何が入るのかが分かるか（「まだプロジェクトがありません」のように、対象の名前を含む）。
- 最初の操作へ直接進めるか（作成ボタン、インポート、テンプレート選択などの導線がその場にある）。
- 利用者に操作権限がない場合の文言が分かれているか（作成できない利用者に作成ボタンを見せない、または理由を示す）。
- 空になる原因が複数ある場合に区別しているか（初回で空、全件削除して空、絞り込みで 0 件は別の状態である。絞り込みで 0 件は規則 03 で扱う）。
- 初回の案内（チュートリアルやガイド）を出す場合、後回しにでき、あとから同じ案内に戻れるか。
  閉じた案内に戻る手段がないと、利用者は案内を読み終えるまで先へ進めないか、閉じたあとで迷う。

**対象外**：
- 空状態がほぼ発生しない（初期データが必ず存在する画面）。

**別の表現で満たす条件**：
- 空状態が利用者の操作で解消できない（システムが自動生成するデータの一覧など）。
  「いつ、どのような条件でデータが現れるか」を伝えることが次の行動の代わりになるので、その案内があるかで判定する。

**実装上の注意**：
- 空状態のコンポーネントは一覧ごとに書かず、共通化して文言と導線だけを差し替える。
- 空状態の導線は、通常時の作成ボタンと同じ処理を呼ぶ。別の経路を作ると挙動がずれる。

## 03 0 件の理由を残す

**目的**：検索語と条件を残し、すぐ見直せるようにする。

**なぜ効くか**：
0 件になった原因は、検索語の誤り、絞り込み条件の組み合わせ、期間の指定など複数ある。
条件が画面から消えてしまうと、利用者は何を変えれば結果が出るかを推測できない。
入力した検索語と適用中の条件を残し、それぞれを個別に外せるようにすれば、利用者は原因を一つずつ切り分けられる。

**チェック観点**：
- 検索語が入力欄に残っているか。
- 適用中の絞り込み条件が一覧で見えるか（チップやタグなど、条件ごとに表示される形）。
- 条件を個別に解除できるか、または一括でリセットできるか。
- 0 件のメッセージに、何の条件で 0 件なのかが含まれているか（「『株式会社サンプル』に一致するデータはありません」のように）。
- 次の行動を示しているか（条件を変える、キーワードを見直す、新規作成する）。
  似た検索語の候補や最近の検索を出せるなら、利用者が正しい検索語を思い出す負担を減らせる。
- 空状態（規則 02）と区別しているか。データが 1 件もない場合と、条件で絞った結果 0 件の場合では、伝えるべきことが違う。

**対象外**：
- 検索や絞り込みの機能がない一覧。

**別の表現で満たす条件**：
- 条件が一つしかない（単純な検索ボックスのみ）。
  条件の一覧表示や個別解除は不要で、入力欄に検索語が残り、0 件のメッセージにその検索語が含まれていれば満たすと判定する。

**実装上の注意**：
- 条件を URL のクエリに持たせると、リロードや共有でも条件が残る。
- 「フィルターをリセット」は検索語も消すのか、絞り込み条件だけを消すのかを決め、文言で区別する。

## 04 入力内容を失わせない

**目的**：通信失敗時も入力を保持し、再試行だけで戻れる。

**なぜ効くか**：
長い入力を終えて送信した直後に通信が失敗し、入力が消える体験は、利用者にとって最も損失が大きい失敗の一つである。
失敗しても入力が保持され、保存先と状態が見え、再送信の操作が一つで済めば、失敗は軽微な遅延に変わる。

**チェック観点**：
- 送信や保存が失敗したとき、入力内容（添付ファイルの選択も含む）が画面に残っているか。
- 失敗の原因が伝わるか（オフライン、サーバーエラー、入力不備は対処が違う）。
- 入力内容がどこに保存されたかが分かるか（ローカルの下書き、サーバーの下書き、未保存）。
- 再試行の操作が一つで済むか（再送信ボタンが失敗メッセージの近くにあり、押すだけで同じ内容を再送できる）。
- ページを離れたり閉じたりしても復元できるか（ローカルストレージや下書き API への保存）。
- 入力不備による失敗の場合、不備の表示中も他の項目の入力内容が保持されているか（不備の示し方そのものは規則 09 で扱う）。

**対象外**：
- 入力が極めて短い（検索語一つ、チェック一つ）。再入力のコストが再試行の仕組みを作るコストを下回る。

**別の表現で満たす条件**：
- 入力内容に機密性があり、ローカルに残すこと自体がリスクになる（パスワード、決済情報など）。
  機密項目だけを除いて保持し、除いた項目は再入力が必要だと伝えていれば満たすと判定する。

**実装上の注意**：
- 同じ画面での通信失敗と、画面を離れたあとの復元は分けて考える。
  通信失敗の直後は、添付ファイルを含む入力がメモリ上に残っているので、そのまま再送信できるようにする。
  添付の再選択を案内するのは、再読み込みや画面遷移で復元できない場合に限る。
- ローカルへの下書き保存は、送信成功時に必ず消す。古い下書きが次回に復元されると混乱する。
- 添付ファイルは下書きとしてローカルに保持できないことが多い。
  添付を下書きから復元できない場合に限り、復元時にテキスト項目を戻したうえで、添付は再選択が必要である旨を伝える。
- 再送信は多重送信を防ぐ。送信中はボタンを無効化し、サーバー側で冪等性を確保する手段（リクエスト ID など）がなければ提案に含める。

## 05 必要な権限を具体化

**目的**：必要な権限、その権限を持つ管理者、申請方法を一画面で示す。

**なぜ効くか**：
「権限がありません」だけでは、利用者は誰に何を頼めばよいか分からず、管理者を探し回るか諦める。
必要な権限の名前、その権限を付与できる人、申請の手段が同じ画面にあれば、利用者は次の行動に移れる。
管理者側も、具体的な権限名で依頼を受けるほうが対応しやすい。

**チェック観点**：
- どの権限が必要かが具体的に書かれているか（「閲覧権限」「編集者ロール」など、そのアプリの権限名で）。
- 誰がその権限を付与できるかが分かるか（ページの所有者、組織の管理者、担当部署）。
- 申請の手段がその場にあるか（申請ボタン、連絡先、申請フォームへの導線）。
- 権限不足の画面が、存在しないページや障害と区別できるか。
- 権限がないことを伝えつつ、見せてはいけない情報（ページの内容、所有者の個人情報）を漏らしていないか。

**対象外**：
- 権限不足が発生する導線がない（権限のない機能はメニューに出ない設計で、URL の直接入力や共有で到達する経路もない）。
  URL 共有で到達する可能性がある画面は対象になる。

**別の表現で満たす条件**：
- 権限の付与を利用者からの申請で行わない運用（人事システムと連動して自動付与される、など）。
  「申請方法」の代わりに「権限が付与される条件」が示されていれば満たすと判定する。

**実装上の注意**：
- 所有者や管理者の情報を表示する場合、表示してよい範囲を確認する。名前を出せない場合は「管理者に申請」ボタンで通知だけを送る形にできる。
- 申請ボタンは、申請が届く先と、届いたあとの流れ（承認されたら通知される、など）を伝える。
- 権限判定はサーバー側で行い、画面は結果を表示するだけにする。

## 06 保存状態を常に示す

**目的**：未保存、保存中、保存済みを作業中に確認できる。

**なぜ効くか**：
編集画面で利用者が最も不安になるのは「今閉じたら失われるか」である。
保存状態が常に見えていれば、利用者は保存の操作を繰り返したり、閉じる前に迷ったりせずに済む。
自動保存があっても、それが動いていることが見えなければ安心にはつながらない。

**チェック観点**：
- 未保存、保存中、保存済みの三つの状態が区別して表示されるか。
- 表示が作業中の視線の範囲にあるか（ツールバーやフッターなど、常に見える位置）。
- 保存に失敗したときの状態が別に表示されるか（「保存済み」に戻らず、失敗と再試行を示す）。
- 保存中に編集を続けた場合、「保存済み」の表示が現在の編集内容と一致するときだけ出るか。
- 未保存のまま画面を離れようとしたときに警告があるか。
- 最後に保存された時刻が分かるか（複数人で編集する場合や、自動保存の間隔が長い場合）。

**対象外**：
- 閲覧専用の画面。

**別の表現で満たす条件**：
- 明示的な保存ボタンだけで保存し、編集がごく短い（設定のトグル一つなど）。
  常時の状態表示は不要で、保存の成功と失敗が伝わっていれば満たすと判定する。
- 変更が即時に確定する操作（トグルの切り替えが即座にサーバーへ反映される）。
  反映中と反映失敗の表示があれば満たすと判定する。

**実装上の注意**：
- 状態は「未保存」「保存中」「保存済み」「保存失敗」の四つを持つ。遷移は次のとおり。
  - 未保存から保存中（保存の開始）
  - 保存中から保存済み（成功。ただし保存した版と現在の編集内容が一致する場合に限る）
  - 保存中から未保存（成功したが、保存の開始後に編集が加わっている場合。自動保存では既存の保存方針に従って次の保存を開始し、手動保存では未保存を維持する）
  - 保存中から保存失敗（失敗）
  - 保存済みまたは保存失敗から未保存（再編集）
  - 保存失敗から保存中（再試行）
- 保存中の再編集を扱うため、保存の開始時に送った版（内容のハッシュや版番号）を記録し、成功の応答が返ったときに現在の内容と比較する。
  比較せずに成功の応答だけで「保存済み」にすると、後から加えた編集が未保存のまま「保存済み」と表示される。
- 「保存中」が一瞬で終わる場合、表示が点滅する。最短表示時間を設けるか、「保存済み」への遷移だけを見せる。
- 状態の変化は `aria-live` で支援技術に通知する。ただし毎回の自動保存を読み上げると煩わしいので、失敗のみを通知する設計もある。

## 07 削除対象と影響を明示

**目的**：対象、戻せない影響、代替案を決定前に見せる。

**なぜ効くか**：
「削除しますか？」だけの確認は、何を消そうとしているかを利用者に思い出させる負担を残し、確認が形骸化する。
対象の名前、消えたあとに何が起きるか（復元不可、関連データも消える）、削除以外の選択肢（アーカイブ、非表示）が見えていれば、利用者は判断できる。
確認の目的は「はい」を押させることではなく、誤操作を止めることにある。

**チェック観点**：
- 削除対象が名前で示されているか（「このファイル」ではなく「企画書.pdf」）。
- 複数件を削除する場合、件数と代表的な対象が示されるか。
- 戻せるかどうかが明記されているか（完全に削除される、30 日間はゴミ箱に残る、など）。
- 関連するデータへの影響が伝わるか（プロジェクトを削除するとタスクも消える、など）。
- 削除以外の選択肢があるなら提示しているか（アーカイブ、非表示、無効化）。
- 確認ボタンの文言が操作を表しているか（「OK」ではなく「削除する」）。
- 影響が大きい削除で、追加の確認（対象名の入力など）があるか。逆に、影響が小さい削除で過剰な確認になっていないか。

**対象外**：
- 削除や、それに相当する破壊的操作がない画面。

**別の表現で満たす条件**：
- 削除が容易に取り消せる（取り消しボタン付きのトースト、ゴミ箱からの復元）。
  確認ダイアログは省いてよく、削除の直後に取り消しの手段と、取り消せる期限（トーストが消えるまで、ゴミ箱に残る期間）が見えていれば満たすと判定する。
- 削除対象が画面上で既に明らかで、影響が対象そのものに限られる（一覧の行に対する削除で、行の内容が見えている）。
  対象名の再掲は不要だが、戻せないなら「戻せない」ことが伝わっているかで判定する。

**実装上の注意**：
- 代替案（アーカイブなど）は、機能として存在しなければ提示できない。
  存在しない場合は、新設するかどうかを開発者の判断事項として残す。
- 確認ダイアログでは、既定のフォーカスを安全な側（キャンセル）に置く。
- 削除の実行結果（成功、失敗）を伝える。ダイアログが閉じただけでは、消えたのかどうか分からない。

## 08 完了後の流れまで案内

**目的**：受付内容、次の予定、確認方法まで伝える。

**なぜ効くか**：
「完了しました」だけの画面では、利用者は何が受け付けられたのか、この先どうなるのか、あとで確認するにはどうすればよいかを知ることができない。
申請や提出のように、完了後に相手側の処理が続く操作では、利用者の不安は完了の瞬間から始まる。
受付内容、受付番号、次に起きること、確認の場所を示せば、問い合わせや二重提出を減らせる。

**チェック観点**：
- 何が受け付けられたかが分かるか（対象の名前、件数、日時）。
- あとで参照できる識別子があるか（受付番号、注文番号）。
- 次に何が起きるかが分かるか（審査の予定、通知の手段、いつ頃か）。
- 受付内容をあとから確認する場所が示されているか（履歴画面への導線、メール送付の案内）。
- 完了画面から次の操作に自然に進めるか（続けて提出する、一覧に戻る）。
- 完了画面を閉じたあとも、同じ情報にたどり着けるか（履歴画面、通知メール）。
- 画面遷移を伴わない操作では、結果の表示が操作した場所か、その時点で利用者が見ている範囲にあるか。
  視線から離れた場所の変化は見落とされやすく、画面の隅に出るトーストだけでは結果に気づかないまま同じ操作を繰り返すことがある。

**対象外**：
- 頻繁に繰り返す軽い操作（チェックのオンオフ、並べ替え）。完了画面自体が邪魔になる。

**別の表現で満たす条件**：
- 完了後に相手側の処理が続かず、結果が画面上で即座に確認できる操作（設定の変更、名前の変更など）。
  受付番号や次の予定は不要で、変更が反映されたことが伝わっていれば満たすと判定する。

**実装上の注意**：
- 受付番号のような識別子は、バックエンドが発行していなければ表示できない。
  発行の仕組みがない場合は追加開発の候補として分けて書く。
- 「次回の予定」は変わりうる情報なので、確定した日付として書かず、「〇月中旬」「メールでお知らせ」のように幅と手段で伝える。
- 完了画面はリロードしても再送信されないようにする（POST 後のリダイレクト）。
- 画面遷移を伴わない操作の結果は、`aria-live` で支援技術にも通知する。見た目の変化だけでは伝わらない。

## 09 入力不備の直し方を示す

**目的**：どの項目を、どう直せば通るかを、その項目の近くで伝える。

**なぜ効くか**：
入力不備は、通信失敗と違って利用者自身が直さなければ先に進めない。
「エラーが発生しました」や「入力内容を確認してください」だけでは、利用者は全項目を見直すか、思い当たる項目を手当たり次第に直すことになる。
問題の項目、何が問題か、どう直せば通るかが項目の隣にあれば、利用者は直すべき場所に視線を移すだけで済む。
形式の制約（日付の書き方、受け付けるファイルの種類と上限）を入力前に示しておけば、不備そのものが減る。

**チェック観点**：
- どの項目に不備があるかが、その項目の近くに示されるか（画面上部のまとめだけで終わっていない）。
- 何が問題かだけでなく、どう直せば通るかが書かれているか（「形式が不正です」ではなく、「@ を含むメールアドレスを入力」のように直す操作で）。
- 形式や制約のある項目で、入力前に例や制約が見えているか（書式の例、文字数の上限、受け付けるファイル形式と容量）。
- 入力中も項目名が見えているか（プレースホルダーだけを項目名にすると、入力を始めた時点で何の欄か分からなくなる）。
- 不備を表示する時機が適切か（入力を始めた直後に出さず、項目を離れたときか送信時に出す。直したら消える）。
- 不備が複数ある場合、件数と一覧を示し、最初の不備へフォーカスを移しているか。
- 不備の表示が色だけに頼らず、文言やアイコンでも分かるか。
- 不備があっても、他の項目の入力内容が保持されているか（規則 04）。

**対象外**：
- 入力項目がない、または選択式だけで不備が起きない画面。

**別の表現で満たす条件**：
- 検証がサーバー側でしか行えず、送信後にまとめて結果が返る（重複の確認、外部システムとの照合など）。
  項目単位の即時表示はできないので、返ってきた結果を項目の近くに振り分けて表示し、直し方が書かれていれば満たすと判定する。

**実装上の注意**：
- 不備の表示と入力欄を `aria-describedby` で結び、入力欄に `aria-invalid` を付ける。まとめの領域は `aria-live` で支援技術に通知する。
- 直し方の文言は、検証ルールから機械的に生成せず、利用者が取る操作で書く。「正規表現に一致しません」は直し方にならない。
- 入力前の例は、プレースホルダーに置くと入力を始めた時点で消える。項目名の下か欄の外に置く。
- クライアント側の検証はサーバー側の検証の代わりにならない。両方に同じルールを持たせ、文言も揃える。
