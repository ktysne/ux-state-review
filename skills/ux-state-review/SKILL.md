# UI 状態設計の 9 規則

利用者が画面の前で立ち止まる場面（待つ、何もない、失敗した、権限がない、消す、終わった、入力が通らない）で、
次に何が起きるか、何をすればよいかを画面が伝えているかを点検し、足りなければ補うためのスキルである。

## このスキルが守るもの

守るのは規則とその目的であり、特定の見た目ではない。
規則の説明に出てくる文言や画面構成は理解を助けるための例であり、アイコンの有無、ボタンの並び、文言そのものを揃える必要はない。

適用の可否は、対象アプリの性質（利用者、利用頻度、業務上の重要度、既存の UI 規約、技術的制約）を踏まえて判断する。
規則を機械的に当てはめると、社内ツールに過剰な装飾を足したり、一瞬で終わる処理に進捗表示を付けたりして、かえって使いにくくなる。
各規則の「適用しない条件」を必ず確認してから提案する。

## 進め方

1. **対象の把握**：どの画面、コンポーネント、フローを扱うかを特定する。
   アプリ全体の性質（業務システムか、一般消費者向けか、開発者向けか）と既存のデザインシステムや UI 規約を確認する。
   画面構成は、画面のルーティングとコンポーネントの一覧から把握する。
2. **状態の洗い出し**：対象ごとに、規則が関係する状態を列挙する。
   読み込み中、空、検索 0 件、送信失敗、権限不足、編集中、削除確認、完了、入力不備の 9 状態が対象になる。
   その画面に存在しない状態は対象外として記録する（例：検索機能がない一覧に規則 03 は関係しない）。
3. **規則ごとの判定**：該当する状態について、[references/rules.md](references/rules.md) のチェック観点で現状を確認する。
   判定は「満たす」「満たさない」「適用しない（理由）」「情報不足（確認事項）」の四つに分ける。
   「適用しない」にできるのは、その状態が起きないか、起きても利用者が困らない場合に限る。
   チェック観点どおりの表示ができなくても別の手段で目的を達成できる場合は、rules.md の「別の表現で満たす条件」に従い、その手段の有無で「満たす」「満たさない」を決める。
   説明文や画面だけでは分からない状態（成功時の表示、権限のない利用者の到達経路、削除機能の有無など）は、推測で判定せず「情報不足」として確認事項を添える。
4. **適用**：「満たさない」ものについて、そのアプリの UI 規約に沿った直し方を提案するか、依頼されていれば実装する。
   直し方は規則の目的から導く。規則の説明にある例をそのまま持ち込まない。
5. **報告**：後述の形式で結果をまとめる。

レビューだけを依頼された場合は 4 を提案にとどめる。
実装を依頼された場合も、規則の適用可否に判断が分かれる箇所は提案として残し、確実な箇所だけを実装する。

## 9 つの規則

各規則の詳細なチェック観点、適用しない条件、実装上の注意は [references/rules.md](references/rules.md) にある。
判定するときは必ず参照する。

| 番号 | 規則 | 目的 | 対象となる状態 |
|---|---|---|---|
| 01 | 待ち時間を見える化 | 何を待っているか、どこまで進んだかが分かれば離脱が減る | 読み込み中、処理中 |
| 02 | 空状態に次の行動を | 空白を行き止まりにせず、最初の操作へつなぐ | データが 1 件もない |
| 03 | 0 件の理由を残す | 検索語と条件を残し、すぐ見直せるようにする | 検索や絞り込みの結果が 0 件 |
| 04 | 入力内容を失わせない | 通信失敗時も入力を保持し、再試行だけで戻れる | 送信や保存の失敗 |
| 05 | 必要な権限を具体化 | 必要な権限、管理者、申請方法を一画面で示す | 権限不足 |
| 06 | 保存状態を常に示す | 未保存、保存中、保存済みを作業中に確認できる | 編集中 |
| 07 | 削除対象と影響を明示 | 対象、戻せない影響、代替案を決定前に見せる | 削除や破壊的操作の確認 |
| 08 | 完了後の流れまで案内 | 受付内容、次の予定、確認方法まで伝える | 処理の完了 |
| 09 | 入力不備の直し方を示す | どの項目をどう直せば通るかを項目の近くで伝える | 入力不備（検証エラー） |

## 適用判断の原則

規則を当てはめるかどうかは、次の順で考える。

- **その状態が実際に起きるか**：起きない状態に備える UI は不要である。
  たとえば削除機能がないなら規則 07 は対象外であり、自動保存のない閲覧専用画面なら規則 06 は対象外である。
- **利用者がその状態で困るか**：困らないなら規則の目的が成立しない。
  困るが、チェック観点どおりの表示ができない場合は「適用しない」ではなく、別の手段で目的を満たせるかを見る。
  100 ミリ秒で終わる読み込みに進捗表示を足しても、利用者は待っていると感じる前に終わる。
  規則 01 は、待ち時間が体感できる長さ（目安として 1 秒以上）になりうる処理に効く。発生頻度が低くても、起きたときに長く待たせる処理は対象に含める。
- **既存の規約と衝突しないか**：アプリにデザインシステムや共通コンポーネントがあるなら、その語彙で実現する。
  規則の目的を満たす別の表現が既にあるなら、それを「満たす」と判定してよい。
- **コストに見合うか**：規則を満たすためにバックエンドの変更（進捗 API、権限の所有者情報、受付番号の発行など）が必要な場合がある。
  その場合は、フロントエンドだけで実現できる部分と、追加開発が必要な部分を分けて提案する。

判断に迷ったときは、規則の目的（表の「目的」列）に立ち返る。
目的が満たされていれば手段は問わない。

## 報告の形式

レビュー結果は次の形式でまとめる。
対象が多い場合は画面ごとに繰り返す。

```markdown
## 対象
（画面やコンポーネントの名前と、アプリ全体の性質の要約）

## 判定
| 規則 | 判定 | 現状 | 提案 |
|---|---|---|---|
| 01 待ち時間 | 満たさない | 一覧の初回読み込みでスピナーのみ | スケルトン行と件数の進捗表示 |
| 02 空状態 | 満たす | 作成ボタン付きの空表示あり | なし |
| 03 0 件 | 適用しない | 検索機能がない | なし |
| 05 権限不足 | 情報不足 | 権限のない利用者が到達する経路が不明 | 到達経路を確認してから再判定 |
| ... | | | |

## 優先して直す項目
（利用者への影響が大きい順に、理由を添えて）

## 判断を委ねる項目
（適用の可否がアプリの方針に依存するもの。選択肢と推奨を添えて）
```

「判断を委ねる項目」には、規則の適用によって開発者が決めるべきこと（代替案としてアーカイブ機能を新設するか、進捗 API を追加するか、など）を残す。
自走中はメインセッションの判断で推奨案を採り、決めるべき内容は一覧にして開発者に提示する。

## 実装時の注意

- 文言は、そのアプリの既存の文言のトーン（敬体か常体か、専門用語の使い方）に合わせる。
- 状態表示は、見た目だけでなく支援技術にも伝わるようにする。
  読み込み中や保存状態の変化は `aria-live` 領域か同等の仕組みで通知し、ダイアログにはフォーカス管理を付ける。
- 状態の区別（選択中、入力不備、保存済み、処理中）を色だけに頼らず、文言、アイコン、形でも区別する。
  色の違いだけでは、色覚特性や画面環境によって区別できない利用者が出る。
- 状態の変化は、操作した場所の近くで伝える。
  視線から離れた場所の変化は見落とされやすく、利用者は結果が出ていないと思って同じ操作を繰り返す。
- 状態から次へ進むボタンやリンクの文言は、押した結果が分かる語にする（「送信」より「予約を確定する」、「詳しくはこちら」より「料金プランを比較する」）。
  押した先で何が起きるかが分かれば、利用者は状態の途中で立ち止まらずに済む。
- 状態の遷移（未保存から保存中、保存中から保存済み、失敗から再試行）を実装するときは、
  どの状態からどの状態へ移れるかを先に決め、遷移表として残す。
  状態が増えるほど、表示の抜けは遷移の抜けから生まれる。
- 変更後は、対象の各状態を実際に再現して確認する（ネットワークを切る、権限のないアカウントで開く、空のデータで開く）。
  再現方法がない状態は、確認できていないと報告に書く。
